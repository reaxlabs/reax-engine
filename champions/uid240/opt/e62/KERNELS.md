# KERNELS.md: compiled parts of this image and how to rebuild them

Every native binary we add to the vLLM 0.30.0 base image is listed here: the .so path, its CUDA source and the exact
build line. The Blink engines load their .so files with importlib (`spec_from_file_location`), the Jeffan engine with
`torch.ops.load_library`; nothing is compiled at start. The torch cpp_extension build directories (.o, build.ninja, .ninja_*) are not in the image.

Deterministic build: after linking, every shipped .so goes through one fixed post-step,

```
strip --strip-unneeded <file>.so        # GNU strip (GNU Binutils for Ubuntu) 2.42, from the base image
```

It removes the static symbol table (.symtab / .strtab) only; code, data, the CUDA fatbinary and the dynamic symbols
(PyInit_*) are untouched. Without it a rebuild differs in exactly one place: nvcc names a local FILE symbol after its
temporary file, tmpxft_<nvcc PID in hex>_00000000-6_<name>.cudafe1.cpp, so the bytes depend on the process ID the
build happened to get. With the post-step, independent rebuilds from these sources give the sha256 listed below.
The two Jeffan libraries need one more flag, `-frandom-seed=<library name>` (set in /opt/jeffan/gemm/build_fp8gemm.py):
their sources have internal-linkage device code, which nvcc otherwise names after the cudafe++ process id (in the
fatbinary and .rodata, so strip cannot remove it).

Toolchain (all from the base image): torch 2.13.0+cu130, CUDA 13.0 (nvcc release 13.0, V13.0.88), host compiler
c++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0, NVIDIA CUTLASS 4.5.0 headers as bundled with flashinfer 0.6.18.post1 at
`/usr/local/lib/python3.12/dist-packages/flashinfer/data/cutlass` (include/ and tools/util/include/). Target sm_120a
(RTX PRO 6000 Blackwell). Sources: ours, Apache-2.0; CUTLASS: BSD-3-Clause, NVIDIA Corporation.

### /opt/blink/gemm/bmoe69.so (E69)

Source: `/opt/blink/gemm/bmoe69.cu` (byte-identical copy of `/opt/blink/bmoe69.cu`): team ruj's bmoe kernels (bj/moe,
Apache-2.0, from blink_moegemm.cu) + E69's knobs. Built in the base image (nvcc 13.0 V13.0.88, torch 2.13.0+cu130) with


### /opt/vision/gemm/vattn.so (V2, A1/A2: exact vision-tower attention)

Exact attention forward for the Gemma4 vision tower (VIS_ATTN=1; real rows only with VIS_UNPAD=1). It is loaded by
/opt/vision/vattn.py through importlib `spec_from_file_location`. vfuse.py imports vattn.py only when VIS_ATTN=1.

**What it replicates.** HF Gemma4VisionAttention calls torch SDPA with the encoder's 4-D bool padding mask. PyTorch
runs that as `fmha_cutlassF_bf16_aligned_64x128_rf_sm80`, its memory-efficient kernel (bias variant). This is PyTorch's
copy of the xformers cutlassF forward (BSD-3-Clause). vattn.cu is our own code. It reproduces that kernel's float-op
sequence exactly: the decode is from the public kernel_forward.h source, shipped in the torch wheel's include tree, and
from the SASS of torch 2.13.0+cu130's libtorch_cuda.so, sm_120 cubin. The steps:
- mma.m16n8k8 bf16 chains for Q K^T and P V, in increasing k order;
- an FMUL by the scale, then an FADD of the bias, then an FMUL by log2(e). The SASS shows no FFMA contraction;
- 128-key online-softmax blocks;
- exp2f = ex2.approx with the non-ftz range fix;
- the reference's row-sum order;
- P rounded to bf16 (round to nearest even);
- the final IEEE reciprocal, then an FMUL, then the bf16 store.

Only the scheduling is ours:
- 16 query rows per warp, with P kept in registers;
- no 128-wide padding of the value dim;
- cp.async K/V tiles;
- the order of independent work. The default kernel (variant 0, fwd3_kernel):
  - runs 4 warps (64 query rows) with single K and V buffers, so two CTAs share an SM;
  - post-processes each group of 4 key tiles right after its Q K^T MMAs;
  - does exp2, the row-sum terms, the bf16 pack and the P V MMAs tile by tile.
- Variants 1-3 (VIS_ATTN_VARIANT) compute the same bits with other schedules. Variant 2 is the first version
  (9ab3c07c).

Ours (V2), Apache-2.0; no CUTLASS, xformers or PyTorch code is included.

### /opt/vision/gemm/vis_ops.so (V3, E3 + E4: exact fused GEMM epilogue, norm chains, head norms + RoPE of the vision tower)

Exact fused kernels for the Gemma4 vision tower (VIS_E3=1, VIS_E4=1; each default off). vfuse.py loads the library
through importlib `spec_from_file_location` (`_vo()`, directory VIS_OPS_DIR, default /opt/vision/gemm).

**What it replicates.** The eager batch-invariant reference runs the tower as vLLM 0.30.0 + HF transformers 5.17
Gemma4 modules with VLLM_BATCH_INVARIANT=1.
- `gelu_up` (E3): one CUTLASS dual GEMM computes gate = x Wg^T and up = x Wu^T. It uses mma.sync m16n8k16
  bf16 -> fp32, no split-k, and warp K = threadblock K (no sliced-k). So each element has the same increasing-k
  16-wide MMA chain as vLLM's batch-invariant Triton matmul and our blink_gemm CUTLASS GEMM. The epilogue then:
  - rounds gate and up to bf16 (the tensors eager stores);
  - computes ATen's tanh-GELU of the bf16 gate in float, with the same expression and constants as
    ActivationGeluKernel.cu (FMA contraction as nvcc emits it there);
  - rounds to bf16, multiplies by the bf16 up in float, and rounds to bf16 (ATen's bf16 mul).
- `rms_norm`, `norm_res_norm` (E4) compute HF Gemma4RMSNorm on rows of 1152:
  - x.float().pow(2), then vLLM's batch-invariant `mean_kernel` (Triton, 4 warps, BLOCK 1024);
  - its reduction tree is copied from the compiled kernel (TTGIR + PTX, decoded 29 Oct; layout sizePerThread 4):
    - per 1024-chunk, thread t sums elements 4t..4t+3 then 512+4t..512+4t+3, sequentially;
    - xor-butterfly 16, 8, 4, 2, 1 inside the warp;
    - (w0 + w2) + (w1 + w3) across warps;
    - chunks summed from 0.0;
  - the mean is `div.full.f32` (as the Triton kernel), then + eps, `rsqrt.approx.f32`, x * r, * w, bf16;
  - residual adds are bf16 + bf16 in float.
- `qkv_norm_rope` (E4): the q/k/v head norms (rows of 72; the 72-row kernel variant has layout sizePerThread 1).
  - Thread t holds element t; per-warp butterfly; (w0 + w2) + (w1 + w3).
  - Then HF's 2-D axial RoPE on q and k: two 36-channel parts, rotate_half per part, bf16 rounding after each
    product and after the sum.
  - Writes contiguous [rows, 16, 72] q, k, v: the stock layout, which V2's vattn requires.
- Masked lanes of the reference add +0.0 to sums of squares (>= +0), which never changes a value. The kernels keep
  the association order of every nonzero term.

Ours (V3), Apache-2.0. The dual-GEMM headers in /opt/vision/vis_dual/ are NVIDIA CUTLASS examples/45_dual_gemm,
unmodified (BSD-3-Clause, NVIDIA Corporation).

- Source: `/opt/vision/gemm/vis_ops.cu` (byte-identical copy of `/opt/vision/vis_ops.cu`) + `/opt/vision/vis_dual/`.
- Build: `cd /opt/vision && MAX_JOBS=6 python3 build_vis_ops.py`.
  - Steps: torch.utils.cpp_extension.load + ninja in /opt/vision/gemm/vis_ops_build, with -frandom-seed=vis_ops; then
    move vis_ops.so to /opt/vision/gemm/, strip --strip-unneeded, copy vis_ops.cu next to it, and remove the build
    directory.
  - Toolchain: base image (nvcc 13.0 V13.0.88, torch 2.13.0+cu130, c++ 13.3.0), CUTLASS 4.5.0 headers from flashinfer.
  - The sources must sit at /opt/vision: the path is part of the binary.
